# ТЗ: Виджет "Progress Tracking"

## 1. Контекст и цель

"Progress Tracking" — новый дашборд-виджет YouTrack, построенный на основе
существующего виджета "Issues Progress" (`src/widgets/issues-progress/`).
Сохраняет Gantt-визуализацию времени задач в статусах, но:
- добавляет группировку задач по значению поля-справочника (enum custom field),
  при этом **каждая группа рендерится отдельной диаграммой** (не секцией
  внутри одной общей диаграммы);
- заменяет ручные пороги Lead Time (LT50/LT80) на автоматически вычисляемые
  перцентили лид-тайма **для каждой группы отдельно**, по выборке решённых
  задач этой группы;
- сама диаграмма при этом показывает все задачи, попавшие под фильтр
  (resolved и открытые) — ограничение "только resolved" действует **только**
  для расчёта перцентилей фона, не для состава диаграммы.

Основной сценарий использования: сравнение фактического распределения лид-тайма
разных типов/категорий задач (например, Bug vs Feature vs Task) без ручной
настройки нормативов — виджет сам показывает, где на самом деле лежат
50-й и 80-й перцентили каждой группы, закрашивая фон соответствующими зонами.
Отдельные диаграммы на группу выбраны намеренно с расчётом на будущее
усложнение (больше визуальных элементов на диаграмме) — единая диаграмма
на все группы быстро станет нечитаемой.

## 2. Пользовательские сценарии

1. Тимлид добавляет виджет на дашборд, выбирает проект, основной фильтр
   (например `State: Resolved`) и оставляет группировку по умолчанию (Type).
   Виджет строит отдельную Gantt-диаграмму для каждого значения Type
   (Bug/Feature/Task/…), с общим для всех диаграмм шагом сетки по оси X,
   и в фоне каждой диаграммы — зелёная/жёлтая/красная зона по перцентилям
   лид-тайма именно этого типа задач (посчитанным по решённым задачам).
2. Аналитик хочет визуально выделить только задачи с меткой `regression`
   внутри каждого типа: задаёт дополнительный фильтр `tag: regression`.
   Диаграммы показывают все задачи (resolved и открытые), удовлетворяющие
   `основной AND дополнительный`, но зоны фона по-прежнему считаются по
   перцентилям **всех решённых** задач соответствующего типа без
   дополнительного фильтра — чтобы зоны отражали "нормальное" распределение,
   а не искусственно суженную выборку.
3. Пользователь переключает "Группировать по" на другое enum-поле проекта
   (например `Priority`) — набор диаграмм перестраивается с новыми группами
   и новыми перцентилями на группу.
4. Пользователь настраивает шаг сетки по оси X (например "5 дней" вместо
   дефолтного), чтобы диаграммы с большим разбросом лид-тайма были компактнее
   и все диаграммы визуально сопоставимы благодаря единому шагу.

## 3. Настройки виджета

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `title` | `string \| undefined` | — | Заголовок блока в шапке дашборда. |
| `projects` | `string[]` | `[]` | Проекты — используются для загрузки статусов, enum-полей для группировки; НЕ используются напрямую как фильтр запроса. |
| `primarySearch` | `string` | `''` | Основной фильтр (YouTrack query). Обязателен. Определяет состав диаграмм (вместе с доп. фильтром) И базу для перцентилей (вместе с `groupByField=значение`). |
| `additionalSearch` | `string` | `''` | Дополнительный фильтр. Опционален; влияет только на состав диаграмм, не участвует в расчёте перцентилей. |
| `groupByField` | `string` | `'Type'`, если такое enum-поле есть в проекте(ах); иначе первое найденное enum-поле, иначе пусто | Технический (или локализованный, matched так же как сегодня `Type`) name поля-справочника (**строго enum**-тип), по которому задачи разбиваются на отдельные диаграммы. |
| `statusOrder` | `StatusOrderItem[]` | `[]` | Как в Issues Progress — задаёт стартовый статус (`statusOrder[0]`) для расчёта `leadTimeStartAt`, и порядок/цвет сегментов стека. Общий для всех диаграмм-групп. |
| `showProjectedLT` | `boolean` | `true` | Маркер текущего Estimated Date как точки на оси лид-тайма (`projectedLeadTimeDays`) — как в Issues Progress. Заменяет собой убранную историю Estimate Date (см. раздел 7). |
| `gridStep` | `number` (дней): `1` \| `7` \| `14` \| `28` | `1` | Шаг сетки/тиков по оси X (в днях лид-тайма), **общий для всех диаграмм-групп** — чтобы диаграммы были визуально сопоставимы. Опции в UI: 1 (день), 7 (неделя), 14 (2 недели), 28 (4 недели) — по аналогии с настройкой Grid Step в Issue State History, но там шаг календарный (день/неделя/месяц), а здесь ось — не календарная дата, а "дней от старта". |
| `sortBy` | `'startDate' \| 'issueNumber' \| 'estimatedDate'` | `'startDate'` | Сортировка задач **внутри каждой диаграммы-группы** (не глобально). |
| `refreshInterval` | `number` | `0` | Минуты автообновления; 0 = выключено. |
| `debugMode` | `boolean` | `false` | Показ истории переходов статусов под диаграммами. |
| `description` | `string` | `''` | Markdown-текст под диаграммами. |

Убрано относительно Issues Progress: `search` (заменён на `primarySearch` +
`additionalSearch`), `ltEnabled`, `ltSettings`, `showEstimateDate` (галочка и
история тиков — см. раздел 7).

Сериализация в `StoredWidgetConfig` следует тому же паттерну, что в
`issues-progress/types.ts` (`parseStoredConfig`/`serializeConfig`): булевы
поля как строки `'true'`/`'false'`, массивы/объекты — JSON-строки, `gridStep`
— число (как в `issue-state-history`, где `gridStep` тоже примитив).

## 4. Логика отрисовки диаграмм

- Тип диаграммы: построчные Gantt-полосы, идентичные Issues Progress
  (стек сегментов по `StatusSegment[]`).
- **Каждое значение поля группировки рендерится отдельной диаграммой**
  (отдельный `<svg>`/блок), а не секцией одной общей диаграммы. У каждой
  диаграммы — собственный заголовок (имя группы + число задач), собственная
  Y-ось (список задач группы), но **общий шаг сетки по оси X** (`gridStep`)
  и единый принцип масштабирования, чтобы диаграммы можно было визуально
  сравнивать друг с другом (домен X у каждой диаграммы может отличаться по
  максимуму, но сама сетка — с одинаковым шагом в днях).
- Порядок диаграмм-групп: **по алфавиту** значения поля группировки.
- Внутри каждой диаграммы — сортировка по `sortBy`, применяемая **только к
  задачам этой группы** (не глобально ко всему датасету).
- **Состав диаграммы**: все задачи, удовлетворяющие
  `основной_фильтр AND дополнительный_фильтр AND groupByField = G`, —
  включая нерешённые (открытые). Ограничение "только resolved" относится
  **только** к выборке для расчёта перцентилей фона (раздел 5), не к составу
  самой диаграммы.
- Сегменты, `leadTimeStartAt`, `totalDays`, `projectedLeadTimeDays` —
  вычисляются той же логикой, что в Issues Progress
  (`parseStateSegments`/`findLeadTimeStartAt`/`buildIssueChartData`), без
  изменений в алгоритме, включая открытые задачи (для них `totalDays`/маркер
  считается по текущий момент, как и сегодня в Issues Progress).

## 5. Логика расчёта перцентилей

**Выборка для группы G** (используется только для фона, не для состава
диаграммы): все задачи, удовлетворяющие
`основной_фильтр AND groupByField = G AND resolved != null`
(дополнительный фильтр в эту выборку НЕ входит).

**Лид-тайм задачи** = `(issue.resolved - leadTimeStartAt) / MS_PER_DAY`, где
`leadTimeStartAt` вычисляется через `findLeadTimeStartAt` с тем же
`statusOrder`, что настроен в виджете (тот же алгоритм, что в Issues
Progress: первое вхождение в `statusOrder[0]`, id-или-имя матчинг, fallback на
`issue.created`).

**Формула перцентиля**: линейная интерполяция (эквивалент Excel
`PERCENTILE.INC` / numpy `'linear'`, метод R-7) — подтверждено пользователем.
Для отсортированного по возрастанию массива `days[0..n-1]` и перцентиля `p`
(0–100):
```
index = (p / 100) * (n - 1)
lower = floor(index), upper = ceil(index)
value = days[lower] + (days[upper] - days[lower]) * (index - lower)
```
При `n = 1` — единственное значение используется как и p50, и p80.
При `n = 0` (в группе нет решённых задач) — фон зоны для этой группы не
рисуется (нет данных), но сама диаграмма группы всё равно рендерится, если
в ней есть открытые/нерешённые задачи, попавшие под основной+доп. фильтр.

**Источник данных для расчёта**:
- Если `additionalSearch` пуст — **среди resolved-задач** группы G из уже
  загруженного основного датасета (`основной_фильтр`) выборка эквивалентна
  выборке для перцентилей; отдельный REST-запрос не нужен, перцентили
  считаются из уже загруженных данных (отфильтрованных по `resolved != null`).
- Если `additionalSearch` не пуст — требуется отдельный REST-запрос на
  `основной_фильтр AND groupByField = G` (issues + их активности) для
  каждой группы, представленной в отображаемом датасете, т.к. выборка для
  перцентилей шире, чем то, что отрисовывается.

## 6. Визуальное оформление фоновых зон

- На каждой диаграмме-группе, по всей высоте (все строки задач этой группы),
  рисуются 3 фоновых прямоугольника (позади сегментов задач, за строками):
  - `0 → p50 группы`: зелёный (рекомендуется `#E8F5E9`/полупрозрачный зелёный,
    чтобы не конфликтовать с цветами сегментов статусов).
  - `p50 → p80`: жёлтый (`#FFF8E1`/полупрозрачный).
  - `p80 → maxDomain`: красный (`#FFEBEE`/полупрозрачный).
- Координаты X — по собственной `xScale` данной диаграммы (свой домен на
  каждую группу, т.к. диаграммы отдельные), но с сеткой, привязанной к
  общему `gridStep`. Значения p50/p80 — в днях, свои для каждой группы.
- Полупрозрачность обязательна, чтобы не "забивать" цвета сегментов статусов
  и легенду.

## 7. Что убрано по сравнению с Issues Progress

- Чекбокс "Enable Lead Time thresholds" и связанные per-type поля LT50/LT80
  (`ltEnabled`, `ltSettings`) — полностью удалены из конфигурации и рендера.
  Вместо ручных порогов — автоматические перцентили по группам (раздел 5).
- Единое поле `search` — заменено на `primarySearch` + `additionalSearch`.
- **История Estimate Date** (`showEstimateDate` — галочка "Show Estimate Date
  history" и рендер последовательных тиков-меток изменений даты) — убрана
  полностью, вместе с настройкой. Точка, соответствующая **текущему**
  значению Estimated Date, остаётся — это существующий маркер
  `showProjectedLT` (зелёная метка `projectedLeadTimeDays`), который и так
  сохраняется в новом виджете. Отдельного нового элемента для этого не
  требуется.
- Единый (несекционированный) список задач на одной диаграмме — заменён на
  набор отдельных диаграмм, по одной на группу.
- Глобальная сортировка — заменена на сортировку внутри каждой диаграммы-группы.

## 8. Явные допущения

1. "Поле-справочник" для группировки — **строго enum**-тип
   (`fieldType.valueType` содержит `enum`, с непустым `bundle.values`).
   State/Version/Build/OwnedField/User и прочие bundle-подобные типы полей
   не считаются кандидатами на группировку — подтверждено пользователем.
2. `gridStep` реализуется по образцу `GridStep`-настройки из
   `issue-state-history`, но т.к. ось X здесь измеряется в днях лид-тайма
   (не в календарных датах), значение — число дней между тиками/сеткой,
   а не enum `'day'|'week'|'month'`. Набор опций в UI (`Select`, по аналогии
   с `GRID_STEP_OPTIONS`) — фиксированный, **подтверждено пользователем**:
   `1` (день), `7` (неделя), `14` (2 недели), `28` (4 недели). Значение по
   умолчанию — `1`.
3. Combined-запрос "основной AND дополнительный" реализуется как
   `(${primarySearch}) and (${additionalSearch})` (явный оператор `and`),
   а запрос для перцентилей группы — `(${primarySearch}) and (${groupByField}: {${value}})`
   с YouTrack-синтаксисом `{...}` для значений с пробелами.
4. Диаграммы групп рендерятся вертикально одна под другой в порядке
   алфавита; общий вертикальный скролл виджета, как сегодня в Issues Progress.
