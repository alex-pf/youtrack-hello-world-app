# Техническая постановка: индикатор добавления/удаления дочерних задач

Виджет: `src/widgets/issue-state-history/` (Gantt-подобный чарт истории состояний issue).

Статус: постановка на основе изучения текущей кодовой базы (без внесения изменений в код). Все неоднозначности, которые возникли при чтении задачи продакта, разрешены ниже с обоснованием — открытых вопросов для разработчика оставлено по минимуму (см. раздел 9).

---

## 1. Краткое описание фичи и бизнес-цель

На Gantt-баре каждой issue нужно показывать факты изменения состава её дочерних задач (сабтасков) во времени — отдельно от статус-сегментов и уже существующих индикаторов (Estimated Date marker/flag, Blocked-период).

Бизнес-цель: дать пользователю дашборда возможность увидеть на временной шкале issue, когда именно у неё появлялись/пропадали дочерние задачи, не открывая саму issue и не листая её Activity-таб.

Учитывается **только** связь типа "Родитель для" (YouTrack link type `Subtask`, направление, при котором ТЕКУЩАЯ issue — родитель, т.е. `"Родитель для"` / `"Parent for"` / нейтральное имя типа связи `"Subtask"` с `direction: OUTWARD` в терминах API). Обратное направление ("Подзадача для" / `"Subtask of"` / `direction: INWARD`, когда сама issue — чей-то ребёнок) — **игнорируется полностью**, как и любые другие типы связей (Relates, Duplicates, Depends on, Cloned, и т.д.).

Индикатор — круглая точка (dot) на временной оси, привязанная к моменту (activity) изменения состава дочерних:
- **зелёная** — если в этот момент добавилась хотя бы одна дочерняя задача (net-прирост);
- **жёлтая** — если в этот момент дочерняя задача была отвязана/удалена (net-убыль).

Тултип показывает количество дочерних задач и их список (номер + заголовок).

## 2. Источник данных

### 2.1 Активности связей — новый источник, ранее не используемый в проекте

Проверено по всей кодовой базе (`grep -rn "links\|childIssues\|linkType\|LinksActivityItem" src`): ни один из виджетов (`issue-state-history`, `issues-progress`) сейчас не запрашивает и не парсит активности по связям issue. Это **полностью новый источник данных** для проекта, требующий нового API-запроса и новых типов.

`resources.ts` сейчас ограничивает выборку активностей константой:

```ts
const ACTIVITY_CATEGORIES = 'CustomFieldCategory,IssueResolvedCategory';
```

Для получения событий по связям её нужно расширить категорией `LinksCategory` (документированная категория YouTrack activitiesPage API для изменений issue links):

```ts
const ACTIVITY_CATEGORIES = 'CustomFieldCategory,IssueResolvedCategory,LinksCategory';
```

### 2.2 Форма активности связи в YouTrack REST API

Активности категории `LinksCategory` возвращаются как объекты с `$type: "IssueLinkActivityItem"` (иногда сериализуется под общим `$type: "ActivityItem"` в зависимости от версии YouTrack — как и в существующем коде, ориентируемся на структуру полей, а не строго на `$type`, аналогично тому, как `filterStateActivities` использует эвристику по `$type`/имени поля, а не жёсткую типизацию). Ключевые поля, которых сейчас нет в `IssueActivityItem`/`ActivityValue` (`types.ts`):

- `added` / `removed` — массив связанных issue-объектов (не `ActivityValue`, а мини-issue: `{ id, idReadable, summary }`), а не enum-значений.
- `field.name` — для связей обычно совпадает с названием типа связи в его текущем направлении (например, `"Subtask"` или локализованное "Родитель для" — нужно НЕ полагаться только на `field.name`, см. ниже).
- `linkType` — объект вида:
  ```
  {
    id: string,
    name: string,              // нейтральное имя типа связи, напр. "Subtask"
    localizedName?: string,
    sourceToTarget: string,    // напр. "Родитель для" / "Parent for" (когда issue — источник)
    targetToSource: string,   // напр. "Подзадача для" / "Subtask of" (обратное направление)
    directed: boolean
  }
  ```
- `direction` (в некоторых версиях API) — строка `"OUTWARD"` / `"INWARD"` / `"BOTH"`, показывающая, с какой стороны сработало изменение относительно issue, для которой запрошены активности. Это поле НЕ гарантированно присутствует во всех версиях API — нужно проверять эмпирически (см. риски, раздел 9).

**Важно про определение направления "Родитель для":** т.к. в проекте уже есть прецедент "поле есть, но его форма не подтверждена на реальных данных" (см. комментарий в `activity-parser.ts` над `buildBlockingIndicators` про Blocked-эвристику как "UNTESTED against real project data"), рекомендуется определять направление СНАЧАЛА по `linkType.name`/`localizedName`, СОВПАДАЮЩЕМУ с семейством "Subtask", и ДОПОЛНИТЕЛЬНО проверять, что это именно исходящее направление (issue является родителем), сверяя `field.name` или `direction` с ожидаемым значением `"Родитель для"` / `"Parent for"` / `"Subtask"`, а не с обратным `"Подзадача для"` / `"Subtask of"`. Из-за отсутствия live-данных этот механизм нужно завести как регэксп-эвристику, аналогичную `BLOCKED_FIELD_NAME_RE`, с debug-панелью для диагностики (см. раздел 4 и 9).

### 2.3 Текущий список дочерних задач issue (для API-запроса "довеска")

Для актуального (на "сейчас") состава дочерних задач нужен отдельный запрос полей issue. YouTrack REST API поддерживает получение связей через `issues/{id}/links` или через `fields=links(...)`/`fields=childIssues(...)` в зависимости от версии; наиболее переносимый вариант — заводить отдельный запрос:

```
GET issues/{id}/links?fields=id,direction,linkType(name,localizedName,sourceToTarget,targetToSource),issues(id,idReadable,summary)
```

Это НЕ используется сейчас нигде в проекте — `ISSUE_FIELDS` в `resources.ts` не включает `links`/`childIssues`. Нужно добавить отдельную функцию (см. раздел 8).

### 2.4 Существующие типы, которые нужно расширить/на которые ориентироваться

- `IssueActivityItem` (types.ts, строки 107-118) — нужно расширить (см. раздел 3), т.к. текущая форма `added`/`removed: ActivityValue[]` не подходит для issue-объектов дочерних задач.
- `ActivityValue` (types.ts, строки 127-133) — можно оставить как есть для custom-field активностей; для связей заведём отдельный тип (не переиспользуем `ActivityValue`, т.к. семантика поля другая: `id/idReadable/summary` вместо `id/name/presentation/value`).
- `ChartIndicator`/`IndicatorKind` (types.ts, строки 222-262) — расширяется новым `kind: 'dot'` (см. раздел 3.2).
- Паттерн парсинга: `parseEstimateDateChanges` + `buildEstimateDateChangeIndicators` в `activity-parser.ts` — прямой аналог для новой фичи по структуре (парсер событий → билдер индикаторов).
- Паттерн "текущее состояние из fields, а не только из activity" — `extractCurrentEstimatedDate` (resources.ts) — аналог для получения текущего списка дочерних через API "довеска".

## 3. Модель данных

Все новые типы — в `src/widgets/issue-state-history/types.ts`.

### 3.1 Активности связей

```ts
// Мини-представление issue, как оно приходит внутри added/removed
// у LinksCategory-активностей (НЕ путать с ActivityValue).
export interface LinkedIssueRef {
  id: string;
  idReadable: string;
  summary?: string;   // может отсутствовать в activity payload — см. раздел 4
}

// Активность изменения связи. Расширяет модель IssueActivityItem доп. полем
// linkType и added/removed в форме LinkedIssueRef[] вместо ActivityValue[].
// Заводим как отдельный тип, а не смешиваем с IssueActivityItem, чтобы не
// усложнять уже работающий разбор custom-field активностей.
export interface IssueLinkActivityItem {
  id: string;
  timestamp: number;
  author: ActivityAuthor;
  category: { id: string };        // ожидается "LinksCategory" (или похожее — см. риски)
  linkType?: {
    id?: string;
    name?: string;                 // нейтральное имя, напр. "Subtask"
    localizedName?: string;
    sourceToTarget?: string;       // напр. "Родитель для" / "Parent for"
    targetToSource?: string;       // напр. "Подзадача для" / "Subtask of"
    directed?: boolean;
  };
  direction?: 'OUTWARD' | 'INWARD' | 'BOTH' | string; // не гарантированно на всех версиях API
  added: LinkedIssueRef[] | LinkedIssueRef | null;
  removed: LinkedIssueRef[] | LinkedIssueRef | null;
}
```

### 3.2 Текущий список дочерних (API "довесок")

```ts
export interface ChildIssueRef {

```

### 3.3 Событие изменения состава дочерних (внутренняя модель парсера)

```ts
export interface ChildLinkChangeEvent {
  changedAt: number;             // timestamp активности (после per-day dedup, см. раздел 4)
  addedChildren: ChildIssueRef[];   // дочерние, добавленные в это событие/день
  removedChildren: ChildIssueRef[]; // дочерние, убранные в это событие/день
  // net > 0 -> зелёный, net < 0 -> жёлтый, net === 0 -> см. раздел 4 (edge case)
  net: number;
  // Накопленный список дочерних НА МОМЕНТ этого события (после применения
  // изменения) — источник данных для тултипа. См. раздел 4 про накопление.
  childrenAsOfEvent: ChildIssueRef[];
}
```

> **Правка тестировщика:** эта модель описывает ОДНО событие на календарный день с ОДНИМ `net`. Но раздел 4.3 для edge-case "в один день и добавили, и убрали" (net=0 по компенсации) требует рисовать ДВЕ точки — то есть `parseChildLinkChanges` в этом случае обязана вернуть ДВА объекта `ChildLinkChangeEvent` для одного и того же календарного дня и одного и того же `changedAt`, каждый со своим "искусственным" net (+1 / -1) и, что важнее, каждый со своим ПОДМНОЖЕСТВОМ `addedChildren`/`removedChildren` (одно событие содержит только `addedChildren`, второе — только `removedChildren`, а не полный список обоих). Модель типа `ChildLinkChangeEvent` этого не запрещает технически (поля не required-exclusive), но текст раздела 3.3 явно не документирует этот инвариант "1 календарный день -> 1 ИЛИ 2 события" и не проговаривает, что при разбиении на 2 события КАЖДОЕ из них содержит только одну из половин (added ИЛИ removed), а не обе. Без этого уточнения разработчик с высокой вероятностью реализует `parseChildLinkChanges` как "1 день = 1 событие всегда" и только потом, читая §4.3, будет вынужден переделывать сигнатуру/семантику функции. **Уточнение:** `parseChildLinkChanges` возвращает `ChildLinkChangeEvent[]`, где для одного календарного дня допустимы РОВНО ДВЕ ситуации: (а) один объект, если день содержит только добавления, только удаления, или добавления и удаления разных задач без полной взаимной компенсации net (net ≠ 0) — в этом случае объект содержит ПОЛНЫЕ `addedChildren`/`removedChildren` за день; (б) два объекта, ТОЛЬКО если net === 0 из-за точной компенсации (см. §4.3) — тогда первый объект содержит весь `addedChildren` дня и пустой `removedChildren` (net условно `+addedChildren.length`), второй — наоборот. Смежный риск: если в день добавили 2 и убрали 1 (net=+1, НЕ ноль) — по тексту §4.2 это остаётся ОДНИМ событием с обоими списками заполненными и итоговым net=+1 (точка зелёная) — это тоже нужно явно проговорить, т.к. неочевидно без примера.

## 4. Логика вычисления событий добавления/удаления связи

Новая функция в `activity-parser.ts`, по аналогии с `parseEstimateDateChanges` + `buildEstimateDateChangeIndicators`.

### 4.1 Фильтрация активностей

```ts
function filterChildLinkActivities(activities: IssueLinkActivityItem[]): IssueLinkActivityItem[]
```

Критерии (все обязательны):
1. `category.id === 'LinksCategory'` (или соответствующая категория, см. риск в разделе 9).
2. `linkType` соответствует семейству "Subtask" (регэксп по `name`/`localizedName`, аналогично `BLOCKED_FIELD_NAME_RE`):
   `/subtask|подзадач/i` на `linkType.name`/`localizedName`, ИЛИ прямое сравнение `sourceToTarget` с `/родитель для|parent for/i`.
3. Направление — **только исходящее** (issue выступает родителем): если поле `direction` присутствует — брать только `direction === 'OUTWARD'`; если `direction` отсутствует (не все версии API его отдают) — ориентироваться на то, что `field.name`/`linkType.sourceToTarget`, использованный в конкретной активности, соответствует именно "Родитель для"/"Parent for" (а не "Подзадача для"). Это единственный надёжный признак направления при отсутствии `direction`.
   Активности с обратным направлением (issue — подзадача) отбрасываются полностью — они не должны попадать даже в подсчёт (иначе можно перепутать "у issue появился родитель" с "у issue появился ребёнок").

Сортировка по `timestamp` по возрастанию (chronologically), как и во всех остальных парсерах модуля.

### 4.2 Построение событий с per-day дедупликацией и группировкой

Отличие от `parseEstimateDateChanges` (которая просто оставляет ПОСЛЕДНЕЕ изменение за день, теряя промежуточные) в том, что для связей **важно не потерять сами добавленные/удалённые issue** — иначе тултип не сможет показать полный список изменений за день. Поэтому дедупликация — это не "оставить последнюю активность", а **слияние (merge) всех активностей одного календарного дня в одно синтетическое событие**:

```ts
export function parseChildLinkChanges(
  activities: IssueLinkActivityItem[]
): ChildLinkChangeEvent[] // без childrenAsOfEvent — оно считается отдельным проходом, см. 4.3
```

Алгоритм:
1. Отфильтровать и отсортировать активности (4.1).
2. Сгруппировать по календарному дню (`toDateString(timestamp)`, уже есть в файле).
3. Для каждого дня: `addedChildren` = объединение (union по `id`) всех `added` из активностей этого дня; `removedChildren` = объединение всех `removed` этого дня.
   - **Edge case — добавили и в тот же день убрали ту же самую дочернюю задачу**: она попадёт и в `addedChildren`, и в `removedChildren` этого дня одновременно. Решение: оставить как есть в обоих списках (это два разных факта — "добавили" и "убрали" в течение дня, тултип должен быть честным), но при расчёте `net` для выбора цвета такая пара взаимно аннулируется (см. ниже).
   - **Edge case — массовое добавление при создании подзадачи** (YouTrack при создании дочерней задачи через "Add subtask" создаёт связь одной активностью; при "мульти-конвертации" чек-листа в подзадачи может быть несколько активностей в одну секунду/день): все они схлопываются в один день -> один `dot`, `addedChildren` содержит все добавленные за день issue. Это соответствует продуктовому духу "не захламлять чарт" (тот же принцип, что и per-day dedup у Estimated Date).
4. `net = addedChildren.length - removedChildren.length` (после этого шага **уже без** дублей, т.к. `id`, встретившийся и там, и там, физически остаётся в обоих списках — на `net` в раздельном подсчёте по спискам, включая пересечение, это не влияет на арифметику: 1 добавление + 1 удаление той же задачи в net даёт корректный вклад `+1-1=0`).
5. `changedAt` для дня — берём **timestamp последней активности этого дня** (тот же принцип, что и в `parseEstimateDateChanges`, для консистентности "конец дня = финальное состояние на этот день").

### 4.3 Выбор цвета точки при net === 0

Если за день было и добавление, и удаление, взаимно компенсирующие друг друга (`net === 0`, но `addedChildren.length > 0` и `removedChildren.length > 0`) — решение: **рисовать ДВЕ точки** в этот день, а не одну неоднозначного цвета — зелёную (для факта добавления) и жёлтую (для факта удаления), сдвинутые на пиксель по X (как соседние маркеры), а не пытаться слить их в одну точку смешанного цвета. Обоснование: по продуктовому ТЗ цвет строго бинарный (зелёный=добавилась, жёлтый=убавилась) — смешанный/третий цвет не предусмотрен; честнее показать оба факта явно, чем скрывать один из них. Технически: `parseChildLinkChanges` в этом случае возвращает ДВА события с одинаковым `changedAt`: одно с полным `addedChildren` дня и **пустым** `removedChildren` (net условно `+addedChildren.length`), второе — наоборот, с полным `removedChildren` и **пустым** `addedChildren` (net условно `-removedChildren.length`). Каждое из двух событий — отдельный `ChartIndicator`, и КАЖДОЕ также проходит через `buildChildrenTimeline` (§4.4) отдельно — `childrenAsOfEvent` для события "добавление" и для события "удаление" в один день с одинаковым `changedAt` технически совпадают (оба отражают состояние ПОСЛЕ обоих изменений дня), это ожидаемо и не ошибка.

Если `net === 0` НЕ из-за компенсации, а из-за отсутствия событий — такого дня в выдаче просто нет (нет активностей — нет события).

> **Правка тестировщика:** см. также правку в §3.3 — этот раздел описывает единственный edge-case, где один календарный день порождает ДВА объекта `ChildLinkChangeEvent` вместо одного; общее правило "1 день = 1 событие" из §4.2 нужно читать как "1 день = 1 событие, ЗА ИСКЛЮЧЕНИЕМ случая полной net-компенсации, тогда 2". Разработчику стоит явно закодировать этот инвариант проверкой в тестах (день с добавлением+удалением РАЗНЫХ задач и net≠0 -> 1 событие с обоими списками; день с добавлением+удалением, где net=0 -> 2 события с разделёнными списками).

### 4.4 Накопление актуального списка дочерних на момент события (`childrenAsOfEvent`)

Отдельная функция:

```ts
export function buildChildrenTimeline(
  changes: ChildLinkChangeEvent[], // отсортированы chronologically
  currentChildren: ChildIssueRef[] // "снимок" на сейчас, из API-довеска (2.3)
): ChildLinkChangeEvent[] // те же события, но с заполненным childrenAsOfEvent
```

Алгоритм — обратный проход (back-fill) от известного "сейчас" к прошлому, а не форвардный от нуля:
1. Стартуем с `currentChildren` (актуальный список из API — самый надёжный источник, т.к. content активности может не содержать `summary`, см. риски).
2. Идём по `changes` от последнего к первому. Перед обработкой события `i` множество `childrenAsOfEvent` для события `i` — это множество ПОСЛЕ применения события `i` (т.е. итоговое множество, каким оно стало сразу после этого добавления/удаления).
3. Чтобы получить множество ДО события `i` (нужно для следующего шага назад), из текущего рабочего множества нужно: убрать те `id`, что были в `addedChildren` события `i` (их тогда ещё не было), и добавить обратно те, что были в `removedChildren` события `i` (они тогда ещё были).
4. Присвоить `childrenAsOfEvent` (для тултипа) = рабочему множеству ПОСЛЕ применения события `i`, ДО отката к состоянию перед событием `i` (т.е. присваиваем перед шагом 3, используя текущее состояние работы "снизу вверх").

Практически: это стандартный "снапшот на каждый момент времени", вычисляемый в один проход с конца. Если данных `summary` для давно удалённых дочерних не хватает (см. риск про summary в activity payload) — оставляем `summary: idReadable` как деградационный fallback (см. раздел 9).

**Почему не форвардный проход от нуля:** issue могла существовать и иметь дочерние ДО того, как включили LinksCategory-активности в выборку, или до истории, которую вернул `activitiesPage` (юбилейное ограничение `$top=1000`, как и у остальных активностей) — вести подсчёт "с нуля" от первой известной активности рискует дать неверную базу (аналогичная проблема с `buildTransitionTimeline`, где недостаточно состояний решается fallback на `extractCurrentState`). Обратный проход от заведомо верного "сейчас" (API-довесок) устраняет этот риск.

### 4.5 Что показывает ПОСЛЕДНЯЯ точка (по аналогии с current-estimate-flag паттерном)

Продакт явно намекнул на паттерн "последний тик показывает текущее значение, а не порядковый номер" (см. `buildCurrentEstimateFlagIndicator` — текущий Estimated Date рисуется ОТДЕЛЬНЫМ индикатором типа `flag`, а не подменяет собой последний `marker`).

Решение: **та же архитектура, 1-в-1 копируем паттерн**, без специальной логики внутри `dot`-точек:
- Каждая `dot`-точка — это событие ИЗМЕНЕНИЯ (добавили/убрали), и её тултип всегда показывает список/количество **на момент этого события** (`childrenAsOfEvent`), НИКОГДА "на сейчас" — так же, как `estimate-date-change` marker-и всегда показывают "было/стало" именно этого изменения, а не текущее значение.
- Текущее (на сейчас) количество и состав дочерних НЕ показывается через последнюю dot-точку. Вместо этого этот факт уже покрывается тем, что последняя точка = последнее событие = `childrenAsOfEvent` последнего события **и есть** текущий список (т.к. обратный проход стартует от `currentChildren`) — если после последнего события состав дочерних больше не менялся, то `childrenAsOfEvent` последней точки автоматически равен текущему состоянию. Отдельный "флаг текущего состояния" (аналог `estimate-date-current` flag) **не требуется**, потому что, в отличие от Estimated Date (у которого "текущее значение" — это одиночный скаляр, который надо явно показать даже если он никогда не менялся), "текущее количество дочерних" осмысленно показывать только в момент, когда оно МЕНЯЕТСЯ — статичный "текущий счётчик дочерних, который никогда не менялся" не несёт для этой фичи такой же ценности, как текущая Estimated Date, и продакт не просил отдельный статичный индикатор. Если у issue дочерние есть, но состав никогда не менялся за время видимой истории — точек не будет вовсе (это осознанное решение, см. риск 9.3).

> **Правка тестировщика (см. также §9.3 и §10):** формулировка "НИКОГДА 'на сейчас'" здесь избыточно категорична и создаёт риск для разработчика. Продакт написал буквально "текущее количество дочерних задач" в тултипе — в русскоязычном UI слово "текущее" почти всегда читается как "по состоянию на сейчас", а не как "исторический срез на момент этого события". Аналогия с `estimate-date-current` flag работает НЕ в пользу выбранного решения, а против него: именно потому что в этом проекте уже есть прецедент отдельного индикатора для "текущего значения", отсутствие такого индикатора для дочерних задач будет выглядеть как непоследовательность, а не как осознанный дизайн. Аргумент "последняя точка часто совпадает с текущим состоянием" верен только пока после последнего события состав не менялся НИКАК ИНАЧЕ, кроме как через связи типа "Родитель для" — но состав может измениться и без событий на графике (например, если дочерняя задача была удалена целиком, а не просто отвязана — см. также риск про API-довесок в §9.2), и тогда последняя точка покажет устаревшее число, а пользователь без наведения на неё вообще не увидит никакого числа. Это прямое расхождение с буквальным текстом ТЗ, а не просто открытый вопрос. Рекомендация разработчику: в тултипе КАЖДОЙ dot-точки показывать явно подписанные ДВА числа — "Дочерних задач на этот момент: N" (из `childrenAsOfEvent`, историческое) и, если это последняя точка на шкале, дополнительно "Дочерних задач сейчас: M" (из `currentChildren`, всегда актуальное) — см. правку в §6.1. Уточнение у продакта, что именно имелось в виду под "текущее количество", остаётся рекомендованным, но не блокирующим, если реализовать оба числа.

## 5. Визуальное представление

### 5.1 Форма и размер

- Форма: **круг** (`<circle>`), а не тик/линия (marker) и не флаг (flag) — визуально отличим от существующих индикаторов.
- Радиус: **3.5px** (`r="3.5"`) — заметно отличается от `marker`-тика (2px ширина линии) и от `hatch`-линии (1.5px), но не крупнее пенанта флага (высота ~6px). Центр по Y — середина ряда, `cy = ROW_HEIGHT / 2` (та же величина `cy`, что уже используется для marker/flag в `gantt-chart.tsx`).
- Обводка (`stroke`): тонкая, `1px`, `var(--ring-content-background-color)` (или белая/фоновая) — чтобы точка не сливалась визуально с status-сегментом под ней, если совпадает по цвету (напр. зелёный сегмент статуса + зелёная точка).

### 5.2 Цвета

- Добавление (net > 0): **зелёный**, `#4CAF50` (переиспользуем существующую константу палитры статусов `STATUS_COLORS[0]` — тот же оттенок, что уже используется в проекте, для консистентности; можно также взять `#22C55E`, использованный в issues-progress для "Projected LT", но `#4CAF50` уже есть в текущем файле и ближе по смыслу "успех/прирост").
- Удаление (net < 0): **жёлтый**, `#FFC107` (Material Amber 500 — не путать с оранжевым `#FF9800`, который уже занят в `STATUS_COLORS` под статус; жёлтый должен быть однозначно отличим от оранжевого статус-сегмента).
- Цвет передаётся через существующее поле `ChartIndicator.color` — рендер-код НЕ хардкодит цвет по `kind`, а берёт `indicator.color` (как и для остальных kind), с fallback в `INDICATOR_DEFAULT_COLOR.dot` (добавить в `gantt-chart.tsx`, например нейтральный `#4CAF50` как дефолт, если color не передан — но producer в `activity-parser.ts` ВСЕГДА будет передавать явный color, т.к. цвет — это сама суть индикатора).

### 5.3 Позиция по оси X/Y

- X: `xScale(new Date(event.changedAt))` — тот же принцип, что и у `marker`/`flag`: дата СОБЫТИЯ ИЗМЕНЕНИЯ связи (день, когда состав дочерних поменялся), а НЕ дата создания дочерней задачи и не текущая дата "сейчас". Это прямая аналогия с `estimate-date-change` marker, который стоит на дате ИЗМЕНЕНИЯ поля, а не на самой оценочной дате.
- Y: центр ряда issue (`ROW_HEIGHT / 2`), как и остальные point-in-time индикаторы.
- Если в один день зелёная и жёлтая точка (edge case 4.3) — небольшое горизонтальное смещение (`±3px` от `x`), чтобы они не накладывались друг на друга; аналогично тому, как `hatch`-границы рисуют раздельные hit-rect'ы для start/end.

### 5.4 Слой рендеринга и непересечение с другими индикаторами

- Рендерится в том же общем цикле `rows.each(...)` в `gantt-chart.tsx` (строка ~448), где сейчас обрабатываются `marker`/`flag`/`hatch` — просто добавляется новая ветка `if (indicator.kind === 'dot') { ... }` внутри `indicators.forEach(...)`.
- Так как порядок отрисовки — "после status-сегментов", `dot` тоже гарантированно поверх сегментов (не перекрывается).
- Потенциальная коллизия по X: если `estimate-date-change` marker и `child-link-change` dot попадают на одну дату — они рисуются в разных Y (оба по центру строки `cy`), поэтому ВИЗУАЛЬНО НАКЛАДЫВАЮТСЯ друг на друга по одной оси Y. Это тот же риск, что уже существует между `marker` и `flag` в текущем коде (оба используют один `cy`). Смягчение: `dot` — компактная форма (радиус 3.5px), а `marker`/`flag` — вертикальные линии/пеналы; круг поверх вертикальной линии читается нормально (линия видна по бокам от круга), коллизия не критична, дополнительных мер не требуется (те же допущения, что уже приняты для marker+flag в существующем коде).
- Hit-area (см. `INDICATOR_HIT_WIDTH = 12`): для `dot` используем ТОТ ЖЕ инвизибл-rect паттерн (12px шириной, `ROW_HEIGHT` высотой), т.к. видимый круг (7px диаметр) тоже слишком мал для точного наведения — прямая аналогия с существующим комментарием "The visible glyphs are only 1.5-2px wide... hard to hover precisely" (строка 83-87 gantt-chart.tsx).

### 5.5 Легенда

Т.к. в чарте уже есть Легенда для статусов (`.ish-gantt-legend`), но НЕ для индикаторов (marker/flag/hatch легенды сейчас нет вообще — они объясняются только через toggle-панель labels в app.tsx и через тултип при наведении) — решение: **не добавлять отдельную легенду-цвета для dot**, следуя уже принятому в проекте паттерну (Estimated Date и Blocking индикаторы тоже не имеют легенды, только toggle-чекбокс с текстовым label). Единственное место, где объясняется смысл цвета — сам toggle-чекбокс label в app.tsx: `"Child issues added/removed"` (см. раздел 7) и тултип при наведении.

## 6. Тултип

### 6.1 Состав контента

Заголовок тултипа (`tooltipTitle`):
- `"Дочерняя задача добавлена"` — для зелёной точки;
- `"Дочерняя задача удалена"` — для жёлтой точки;
- Если за день добавлено НЕСКОЛЬКО задач: `"Дочерние задачи добавлены"` (множественное число — простая проверка `addedChildren.length > 1`).

Тело тултипа (`tooltipRows`), строго в этом порядке:
1. Строка с количеством дочерних задач **на момент события**: `{ label: 'Дочерних задач на этот момент', value: String(childrenAsOfEvent.length) }`. Формулировка label намеренно уточняющая ("на этот момент"), а НЕ голое "Дочерних задач" / "Текущее количество" — см. правку тестировщика в §4.5: без такого уточнения слово "текущее" будет ошибочно прочитано пользователем как "на сейчас".
2. Если это dot-точка последнего по времени события на шкале issue (т.е. после неё в `changes` больше нет записей) — добавить ЕЩЁ одну строку сразу под п.1: `{ label: 'Дочерних задач сейчас', value: String(currentChildren.length) }`, используя актуальный снимок из API-довеска (§2.3), а НЕ `childrenAsOfEvent`. В подавляющем большинстве случаев (когда после последнего события состав больше не менялся) эти два числа совпадут — это ожидаемо и нормально, дублирование не ошибка, а явное подтверждение пользователю, что показанное число актуально. Для НЕ последней точки эта строка не показывается (было бы двусмысленно показывать "сейчас" в контексте события из прошлого).
3. Разделительная строка-заголовок списка (freeform, `label: ''`): `{ label: '', value: 'Список дочерних задач:' }`.
4. Одна строка на каждую дочернюю задачу из `childrenAsOfEvent`, формат `label: ''`, `value: '<idReadable> — <summary>'`, например `"DEMO-142 — Настроить логирование"`. Сортировка — по `idReadable` (естественный порядок, стабильно воспроизводимо), либо по порядку добавления (хронологически) — выбираем **по idReadable ascending**, т.к. это стабильнее для пользователя при повторных наведениях и не зависит от порядка ответа API.
5. Если `childrenAsOfEvent.length === 0` (все дочерние были удалены к этому моменту) — вместо списка одна строка `{ label: '', value: 'Нет дочерних задач' }`.
6. (Опционально, для симметрии с самим фактом события) — можно добавить отдельную секцию "Изменение:" с explicit added/removed на этот конкретный день, ПЕРЕД пунктом 1, т.к. пользователю полезно видеть не только итог, но и что именно произошло:
   - `{ label: '', value: 'Добавлено: DEMO-142 — Настроить логирование' }` (одна строка на каждую добавленную)
   - `{ label: '', value: 'Удалено: DEMO-098 — Старая подзадача' }` (одна строка на каждую удалённую)
   Это НЕ обязательно, но рекомендуется, т.к. без этого пользователь не отличит "добавили X" от "у X изменился summary" (текущий список этого не покажет). Финальный порядок тултипа (пример для НЕ последней точки — без строки "сейчас"; для последней точки строка "Дочерних задач сейчас" добавляется сразу после "Дочерних задач на этот момент"):
   ```
   [Заголовок: Дочерняя задача добавлена / удалена]
   Добавлено: DEMO-142 — Заголовок           ]  (если addedChildren.length > 0)
   Удалено: DEMO-098 — Заголовок             ]  (если removedChildren.length > 0)
   Дочерних задач на этот момент: 5
   [Дочерних задач сейчас: 5]                    (только для последней точки на шкале)
   Список дочерних задач:
   DEMO-101 — Заголовок 1
   DEMO-102 — Заголовок 2
   ...
   ```

### 6.2 Формат текста

Полностью на русском (проект уже использует русскоязычные тултипы для Blocking/Estimated Date индикаторов — `"Блокировка"`, `"Изменение Estimated Date"`, `"Было/Стало"`), для консистентности используем те же формулировки-паттерны.

```ts
const INDICATOR_TYPE_OPTIONS: IndicatorTypeOption[] = [
  { semanticType: 'estimate-date-change', label: 'Estimate Date change' },
  { semanticType: 'estimate-date-current', label: 'Current Estimate Date' },

```

Дефолт — видимый (`true`), т.к. `visibleIndicatorTypes` инициализируется как `new Set(INDICATOR_TYPE_OPTIONS.map(o => o.semanticType))` — новая опция автоматически попадёт во "все включено по умолчанию", без дополнительного кода.

**Никаких изменений в `configuration.tsx` / `WidgetConfig` / `widget-settings.json` НЕ требуется** — существующая инфраструктура toggle-панели (не персистентная, "session-level" по своему определению в комментарии app.tsx строки 17-23) уже полностью покрывает эту потребность, это ключевой вывод из чтения кода: индикаторы включаются/выключаются НЕ через Configuration-форму, а через чекбоксы над самим чартом.

Единственное, что стоит рассмотреть отдельно (не обязательно, помечено как открытый вопрос с дефолтом) — стоит ли делать доп. запрос за `LinksCategory`-активностями и API "довеском" условным (только если хотя бы один индикатор данного типа включен), чтобы не грузить лишние данные, если фича не нужна пользователю. Дефолт: **не делать условной загрузки** — активности всех категорий (включая новую) загружаются всегда одним и тем же запросом `activitiesPage` (просто добавляем категорию в существующую строку), это не увеличивает число запросов, только объём каждого ответа. API-довесок за текущими дочерними — отдельный новый запрос на issue, обсуждается в разделе 9.2.

## 9. Открытые вопросы / риски (с обоснованными дефолтами)

### 9.1 Точное имя категории/типа активности для связей в конкретной версии YouTrack API
**Риск:** невозможно стопроцентно подтвердить без доступа к реальному YouTrack-инстансу, что категория называется именно `LinksCategory` и что поле `direction` присутствует в ответе (по прецеденту в проекте — сравните с комментарием "UNTESTED against real project data" у `buildBlockingIndicators`).
**Дефолт:** реализовать с `LinksCategory` + fallback-эвристикой по `linkType.sourceToTarget`/`field.name`, как описано в разделе 4.1, и обязательно завести debug-панель (8.3 п.6), которая выводит сырые `added`/`removed`/`linkType`/`direction` для диагностики на первом реальном проекте — по образцу того, как это уже сделано для Blocked-поля. Не блокирует реализацию: если категория окажется иной, потребуется точечная правка одной строки-константы.

> **Постмортем по факту продакшн-теста (2026-07-03):** после мержа фича не работала на реальном проекте — индикаторы вообще не появлялись, несмотря на то что чекбокс в тоггл-панели был включен. Через встроенную debug-панель (`getDebugChildLinkInfo`) получены реальные `LinksCategory`-активности:
> ```json
> {"added":[{"summary":"...","idReadable":"DEMO-20","id":"3-21","$type":"Issue"}],"removed":[],
>  "category":{"id":"LinksCategory"},
>  "field":{"id":"$l3s","name":"Родитель для","$type":"LinkTypeFilterField"},
>  "id":"0-0.14-132","timestamp":1783076089253,"$type":"LinksActivityItem"}
> ```
> Подтверждено: `category.id` действительно `"LinksCategory"`, `added`/`removed` действительно содержат `idReadable`/`summary` — но **`linkType` в ответе отсутствует полностью**, и **`direction` на активности тоже нет**. Единственный реально присутствующий сигнал — `field.name` (тип `LinkTypeFilterField`), который сам по себе уже несёт и "это Subtask-связь", и "в каком направлении" (значение `"Родитель для"` для исходящей стороны, `"Подзадача для"` — для обратной).
>
> Баг был в том, что `filterChildLinkActivities` сначала проверяла `isSubtaskFamily` по `linkType.name`/`localizedName`/`sourceToTarget` и только потом (если это условие уже прошло) смотрела на `field.name` как fallback для направления — но поскольку `linkType` всегда `undefined`, первая проверка всегда возвращала `false`, и функция отбрасывала вообще все активности связей ещё до того, как доходила до `field.name`. Исправлено: `field.name` теперь проверяется первым и является основным (а не запасным) сигналом; проверка через `linkType`/`direction` оставлена как fallback на случай другой версии API. См. правку в `activity-parser.ts` (`filterChildLinkActivities`) от 2026-07-03.
>
> `loadCurrentChildIssues` (эндпоинт `issues/{id}/links`, раздел 2.3) при этом отработал корректно с первого раза — там `linkType`/`direction` в ответе присутствуют по факту, это отдельная от `activitiesPage` API-поверхность.

### 9.2 Источник `summary` дочерней задачи внутри самой activity
**Риск:** неизвестно заранее, включает ли API `added`/`removed` объект дочерней issue с полем `summary`, или только `id`/`idReadable` (аналогичный прецедент — `DateIssueCustomField` вернул примитив там, где ожидался объект).
**Дефолт:** запрашивать `summary` явно в fields-проекции активности (раздел 8.2 п.2); если API его всё равно не отдаёт для добавленных-и-затем-удалённых (более не существующих в текущем составе) задач, комбинировать с данными из API-довеска (`loadCurrentChildIssues`) для ВСЕХ дочерних, известных на "сейчас", и только для тех, что были удалены ДО текущего момента и поэтому не входят в API-довесок — использовать `summary` из самой activity, с graceful fallback `summary ?? idReadable` (показать хотя бы номер, если заголовок недоступен). Это не блокирует реализацию.

### 9.3 Нужен ли отдельный статичный "текущее состояние" индикатор (аналог `estimate-date-current` flag)
**Риск:** продакт мог иметь в виду отдельную визуальную сущность "текущее количество дочерних", видимую даже если состав никогда не менялся — то есть заметную БЕЗ наведения на конкретную точку истории.
**Дефолт (пересмотрен по итогам ревью — см. правки тестировщика в §4.5 и §6.1):** изначальный вариант этого документа предлагал не заводить отдельный индикатор вовсе и полагаться на то, что последняя dot-точка "обычно" совпадает с текущим состоянием — ревью посчитало это недостаточным, т.к. (а) это расходится с буквальным текстом ТЗ продакта ("текущее количество"), (б) если состав дочерних никогда не менялся за видимую историю, точек не будет вовсе и число не покажется НИКАК, даже при наведении, (в) число видно только по hover, а не "с одного взгляда на график", в отличие от что запросил продакт. Принятый после правки компромисс: НЕ вводить отдельный статичный `flag`-индикатор с постоянно видимой подписью на графике (это по-прежнему оправдано — состав дочерних меняется потенциально часто, "флаг" на каждый чих был бы визуальным шумом, plus для issue без единого изменения графически нечего было бы флагать), НО в тултипе последней dot-точки всегда явно показывать текущее число отдельной строкой (см. §6.1). Это НЕ закрывает риск полностью: issue, у которой дочерние есть, но состав НИКОГДА не менялся за видимую историю, по-прежнему не получит вообще никакого индикатора и, соответственно, текущее количество для неё нигде не будет видно без похода в саму issue — **это остаётся открытым расхождением с буквальным ТЗ и обозначено как блокер уровня "требует решения продакта" в §10**, а не как тривиальный доп. пункт, отложенный "после демо".

### 9.4 Активности связей и лимит `$top=1000`/`hasAfter`
**Риск:** т.к. `LinksCategory`-активности добавляются в ТОТ ЖЕ общий список `activitiesPage` (не отдельный запрос), они делят общий лимит в 1000 записей с custom-field-активностями — для issue с очень длинной историей это может привести к обрезанию (уже существующий риск, см. `console.warn` в `loadIssueActivities`, строки 288-293 resources.ts). Дефолт: не решать отдельно для этой фичи — использовать тот же существующий warning-механизм, риск идентичен уже принятому для всего модуля.

## Краткое резюме принятых решений (для продакта/техлида)

1. **Направление связи** определяется строго как "родитель→ребёнок" через `linkType`/`direction`/`sourceToTarget`, с regex-эвристикой по аналогии с уже существующей Blocked-фичей (т.к. это UNTESTED источник данных — заведена debug-панель для диагностики на реальных данных).
2. **Группировка событий за день**: не "оставить последнее" (как у Estimated Date), а слияние всех added/removed за день в одно синтетическое событие, чтобы не терять список изменившихся задач; если в один день одновременно и добавление, и удаление (net=0) — рисуются ДВЕ отдельные точки (зелёная+жёлтая), а не одна смешанного цвета.
3. **Тултип каждой точки показывает состояние "на момент события"** (вычислено обратным проходом от заведомо точного текущего состава — отдельный API-запрос, а НЕ форвардный подсчёт от нуля, так надёжнее при неполной истории активностей), **и дополнительно, только в тултипе последней точки на шкале, явно отдельной строкой показывает актуальное "сейчас"-число** — это уточнение внесено ревью, т.к. буквальный текст ТЗ продакта ("текущее количество дочерних задач") иначе не выполняется однозначно (см. правки в §4.5/§6.1).
4. **Отдельный постоянно видимый "текущий флаг" на графике (аналог current-estimate-date flag) по-прежнему не заводится** — но полностью избежать вопроса "как видно текущее число без hover" не удалось: issue, у которой состав дочерних НИКОГДА не менялся за видимую историю, не получит вообще никакой точки и, соответственно, нигде на графике текущее число не будет видно. Это зафиксировано как открытый блокер для решения продактом, а не как тривиальное расширение "после демо" (см. §9.3, §10).
5. **Toggle реализуется чисто session-level** через существующий `INDICATOR_TYPE_OPTIONS`/`visibleIndicatorTypes` механизм в app.tsx — никаких изменений в `WidgetConfig`, `configuration.tsx` или `widget-settings.json` не требуется, т.к. эта инфраструктура уже полностью общая для всех индикаторов.
6. **Цвета**: зелёный `#4CAF50` (добавление), жёлтый `#FFC107` (удаление, Material Amber, не путать с уже занятым оранжевым `#FF9800`).
7. Категория `LinksCategory` и API-довесок за текущими дочерними (`issues/{id}/links`) — это НОВЫЙ источник данных, ранее нигде в проекте не использовавшийся; требует нового запроса и новых типов, максимально переиспользующих существующие паттерны (`ChartIndicator`, per-issue batch loading, debug-панель).

### Найденные и исправленные проблемы

### Вердикт: готов к реализации

**Решение продакта (получено 2026-07-03):** компромисс "только по наведению" подтверждён — отдельный постоянно видимый статичный индикатор текущего числа НЕ заводится. Тултип каждой dot-точки показывает число "на этот момент", тултип последней точки на шкале дополнительно показывает актуальное "сейчас". Issue, у которой состав дочерних ни разу не менялся за видимую историю, сознательно не получает индикатора вообще (as designed, не баг) — точка ставится только на факт изменения связи, не на факт наличия дочерних задач. Раздел 9.3 и связанный блокер закрыты этим решением.

- **Оговорка (не блокер):** формат ответа YouTrack REST API для `LinksCategory`-активностей (имя категории, наличие `direction`, наличие `idReadable`/`summary` внутри `added`/`removed`) полностью не подтверждён эмпирически — это уже осознанный и правильно помеченный риск в документе (§9.1, §9.2, теперь и в §8.2), с debug-панелью как страховкой. Не блокирует реализацию, но разработчику стоит как можно раньше прогнать debug-панель на реальном проекте с дочерними задачами, прежде чем полировать остальную логику.
